How to create a website for commercial transactions

A shop on the web is a set of pages plus a private server. The customer browses, signs in, fills a cart, and pays. You register the domain, write the HTML, the front end, and the back end, then protect the login and hand the card to a payment company.

Overview

The path of one paid order

Someone finds the shop, chooses a thing, proves who they are, and pays a known amount. Each box below is a piece you will build. The rest of this page is the order to build them in.

  1. ArriveThe domain resolves, and HTTPS opens the catalog.
  2. ChooseThe cart stores product ids and quantities.
  3. Sign inThe server checks a password hash and starts a session.
  4. PayThe payment company takes the card. Your server records the order.

You can buy a hosted shop and skip most of the code. This guide is the other road: your own pages, your own server, and a payment company for the money.

Step 01

Write down the sale before you name the site

Code follows the offer. If the offer is vague, the database and the checkout will be vague too. Spend an hour on paper.

  • What you sell, in one sentence, and the currency.
  • Each product: name, price, stock, a photo, and a short description.
  • Whether a guest may pay, or an account is required.
  • Where you ship, or whether the goods are a file or a service.
  • How a refund works, and in how many days.
  • The seller’s legal name and a contact address customers can use.

Tax and invoices depend on where you and the buyer are. Note the question now. An accountant or your payment company’s tax tool answers it. A guessed rate in the code does not.

Done when a stranger can read your notes and know what is for sale, what it costs, and how to get their money back.

Step 02

Get the domain name

The domain is the address, such as northlinen.example. It is the name people type and the name that appears in emails from the shop. It is not the website itself. The website comes later, on a server the name points to.

  1. Search the name at a domain registrar. Common ones are Cloudflare Registrar, Namecheap, Porkbun, Squarespace Domains, and the registrar for your country.
  2. Pick a name people can say and spell. Skip hyphens and clever misspellings. If the best name is taken, a small change is better than a name customers will mistype.
  3. Register it to yourself or to the company. Keep it off a contractor’s personal account, so you still own it if you part ways.
  4. Turn on automatic renewal. A domain that expires takes the whole shop offline. Put a second factor on the registrar login.
  5. Turn on privacy for the public contact record if you do not want a home address listed in the public directory.
  6. Wait to edit DNS until a host gives you an address. You will then add the records they specify, usually an A record or a CNAME, so the name leads to your server.

Name, directory, machine

Three different things get mixed together. The domain is the name you rent from a registrar. DNS is the directory that maps that name to an address. Hosting is the computer that answers. You can change the host later and keep the same domain, by changing the directory entry.

Done when you can sign in at the registrar, the name is yours, and renewal will happen without you remembering.

Step 03

Choose a host and turn on HTTPS

Hosting is the computer that stores the code and answers visitors. A managed host is the calmer start: you upload the site, and they run the machine. A virtual server is the start when you want to install the app and the database yourself.

Turn on HTTPS before any login or payment page is public. HTTPS encrypts the path between the browser and your server. Browsers mark plain HTTP as not secure, and a password or a checkout on HTTP is not a finished shop.

  • Ask the host for a TLS certificate. Let’s Encrypt is free, and most hosts arrange it for you.
  • Redirect every http:// request to https://.
  • Let the certificate renew on its own. Many of them expire in about 90 days.
  • Open the site by the real domain, so you notice mixed content and broken links while the shop is still private.

Done when the address bar shows a lock, and the http:// address jumps to https://.

Step 04

Plan the HTML pages and the records

Draw the site as a short list of pages, then as a short list of records. The front end is the pages. The back end keeps the records and decides what each page may show.

Done when every moment of a sale has a page, and every fact you must remember has a record.

Step 05

Write the front end

The front end is what the browser draws. HTML names the parts of the page. CSS sets type, space, and a layout that works on a phone. JavaScript reacts to clicks, such as adding an item or showing an error.

Plain HTML, CSS, and JavaScript are enough for a first shop. A framework is a later choice, when the pages grow. The first sale does not depend on one.

The button sends a product id. It does not send a price. The server looks up the price. Build the pages with real labels, buttons, and headings, so the shop works from a keyboard and with a screen reader. Put no secret in the HTML. Anyone can read the page source.

Done when a product page is readable on a phone, and Add to cart sends the sku to your server.

Step 06

Write the back end

The back end is the private half. It reads and writes the database, checks who is signed in, computes money, and holds the only copy of the payment secret. The browser asks. The server decides.

Python, JavaScript on the server, PHP, Ruby, and many other languages can do this job. Pick one you can maintain. A relational database such as PostgreSQL fits orders, because an order, its lines, and its payment status belong together.

A first shop needs a handful of routes:

  • GET /products returns the catalog from the database.
  • POST /api/cart adds or updates a line.
  • POST /login checks the password and starts a session.
  • POST /checkout prices the order and opens payment.
  • POST /webhooks/payment receives the payment result.

That sketch leaves out error messages, validation, and tests. Those belong in the real file. The rule to keep is the one on the page: the charged price is loaded from your database at the moment it matters.

Done when adding the same sku twice updates one line, and the unit price in that line came from the database.

Step 07

Build a secure login

A login is a form, a check, and a session. The form collects an email and a password over HTTPS. The server compares the password with a stored hash. If it matches, the server starts a session and sends the session id in a cookie.

What the account page needs

  • Create account, with a long password. A phrase the customer can remember beats a short puzzle.
  • Sign in, with one message for a bad attempt: “Email or password is wrong.” That avoids telling a stranger which emails are registered.
  • Forgot password. Send a single-use link that expires in about an hour. Store a hash of the token, the way you store a hash of the password.
  • Sign out, which ends the session on the server.

Session cookie

After a successful sign-in, create a new random session id. Setting a fresh id at login closes a class of session mix-ups. Send it as a cookie with three flags:

  • HttpOnly, so page scripts cannot read it.
  • Secure, so the browser sends it only over HTTPS.
  • SameSite, usually Lax or Strict, so other sites cannot quietly use it.

Because the cookie identifies the customer, state-changing forms also need a CSRF token that your server checks. Limit how fast login can be tried, so guessing is slow. Offer a second factor, such as an authenticator app, at least for any staff account that can see orders.

An admin page that lists orders uses the same login, then checks a role on the server. Hiding the link in the HTML is not the check. The route itself refuses a customer account.

Done when a wrong password fails with a generic message, a right password starts a cookie with those three flags, and the password in the database is a hash.

Step 08

Build the shopping cart

A cart is a list of sku and quantity, tied to a signed-in user or to a guest session. The cart page shows each line, lets the customer change a quantity, and shows a total that the server calculated.

  • Adding an item calls POST /api/cart. The server loads the product and writes the line.
  • Changing quantity updates that line. Zero removes it. Quantities are whole numbers.
  • A guest cart lives with a random id in a cookie. When the guest signs in, merge those lines into the account cart.
  • At checkout, read the price and the stock again. If a price changed, show the new total before payment. If stock is short, stop and say so.
  • Keep a copy of the name and unit price on the order line, so a later catalog edit does not rewrite history.

On a real site those four numbers are computed again on the server when the customer presses Pay. The figures in the browser are a preview.

Done when the cart survives a refresh, a guest cart joins the account at sign-in, and checkout rechecks price and stock.

Step 09

Build the secure payment page

The payment page shows the order the server priced: lines, shipping, tax, and total. The card number goes to a payment company such as Stripe, PayPal, Adyen, or Square. Your server stores a payment reference and the order. It does not store the full card number or the security code.

Two patterns keep that promise. In a hosted checkout, you send the customer to the payment company’s page for the card. In an embedded form, their script draws the card fields inside your page, and your server receives a token. In both patterns your secret key stays on the server, and the card data stays with the company that is allowed to hold it. That is also what keeps your own compliance burden smaller.

  1. Beat 01

    The server prices the order

    The customer presses Pay. Your server writes an order with status unpaid. It totals the lines from the database, then adds the shipping and tax it is responsible for. That total is the only amount you will charge.

  2. Beat 02

    Your server opens a checkout

    The server calls the payment company with the order id, the amount in cents, and the currency. The call uses the secret key. The browser never sees that key. The company returns a page or a client token for this exact charge.

  3. Beat 03

    The customer enters the card

    They type the card into the payment company’s form. Your confirmation copy can say, in plain language, that the payment company processes the card and that you do not keep the full number.

  4. Beat 04

    The payment company captures the money

    They approve or decline the charge. A decline returns the customer to the cart with a clear message and the same unpaid order, or a fresh attempt. Stock is still unchanged.

  5. Beat 05

    A signed message reaches your server

    The company sends a webhook. You check its signature before you trust it. Payment companies retry these messages, so marking an order paid must be safe to run twice. A second delivery finds the order already paid and stops.

  6. Beat 06

    You record the sale and show the receipt

    Only after that signed message do you set the order to paid, reduce stock, and send a receipt. The receipt has the order number, the lines, and the total. It has no card data. If the customer lands on the thank-you page early, say that you are confirming the payment until the order status says paid.

Beat 1 of 6

The thank-you address in the browser is a convenience. A customer can open it without paying. The webhook, with a valid signature, is the record that money moved.

Done when a test payment flips an order to paid only after a verified webhook, and the database has no full card number.

Step 10

Publish the pages a shop owes people

A commercial site is also a set of promises. Put them where a customer can find them before they pay, and in the footer of every page.

  • Privacy. What you collect (account, address, order), why, and the payment company that handles the card.
  • Terms of sale. Who the seller is, when the contract is formed, and what happens if an item is out of stock after an order.
  • Refunds. The window, who pays return shipping, and how the money goes back. Refund through the payment company so the order status and the money stay in step.
  • Contact. An email or a form a person can use. Watch it.
  • Receipt. Email the order number, lines, total, and that contact address after the order is paid.

Consumer rules, tax, and what you may store differ by country. This guide cannot settle them. Use the payment company’s tools and a local advisor for the rates and the wording you are required to show.

Done when privacy, terms, refunds, and a contact path are linked from the checkout page.

Step 11

Rehearse a sale in test mode

Payment companies publish test card numbers. Use those. Keep a real card out of test mode. Walk the path as a customer, on a phone width and on a wide screen.

  1. Create an account. Sign in with a wrong password, then the right one.
  2. Reset a password from the email link, and confirm the old sessions ended.
  3. Add items, change a quantity, remove a line, and refresh. The cart should still be there.
  4. Sign in as a guest who already had a cart, and confirm the lines merged.
  5. Pay with a test card that succeeds. Confirm the webhook set the order to paid, stock fell once, and the receipt arrived.
  6. Pay with a test card that fails. Confirm the order stays unpaid and stock does not fall.
  7. Deliver the same webhook again. Confirm the order is not charged twice in your records and stock does not fall twice.
  8. Open the thank-you page for an unpaid order. The page should wait for confirmation.

Done when a successful test sale, a failed test sale, and a repeated webhook all leave the database in a state you can explain.

Step 12

Point the domain, then look after the shop

Launch is the DNS change plus a short list of habits. At the registrar, add the records your host gave you. Wait for the name to resolve. Open the shop on the real domain and confirm the lock, the redirect, a sign-in, and one more test payment before you switch the payment company from test keys to live keys.

  • Keep live secret keys in the server environment. Keep them out of the HTML, out of the repository, and out of screenshots.
  • Back up the database, and try a restore once so you know the backup works.
  • Update the server, the language, and the payment library when they ship security fixes.
  • Log errors. Leave passwords, cookies, and card fields out of the logs.
  • Watch failed payments and failed webhooks. Those are how you find a broken sale.

Search, a richer gallery, and analytics can wait until a real order has gone through. They do not belong on the critical path of the first transaction.

Done when the public domain serves HTTPS, live keys are only on the server, and you have a backup you have restored.
